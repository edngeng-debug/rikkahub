## 🐟 这个版本是什么？

这是一个个人维护的 RikkaHub Fork，目标是把大肥鱼集成进 RikkaHub，同时尽可能少改动原组件的核心表现。

## ✨ 当前功能

- 🐟 RikkaHub 聊天页面显示大肥鱼
- 🖱️ 支持触摸拖动与屏幕范围内移动
- 🧲 支持吸附 / 镜像等相关交互
- 💬 保留大肥鱼的气泡、角色、音效、用量提示等能力
- ⚙️ 将主要设置集中到 RikkaHub 的「扩展 → 大肥鱼」页面
- 🔢 金额、时间、滚动间隔等非百分比参数使用数字输入框
- 💾 设置保存到本地
- 🚫 不再提供大肥鱼本体菜单
- 🚫 不再提供大小设置功能

## 🔧 技术说明

大肥鱼本体主要以 Web UI 形式运行，由 Android `WebView` 承载。Android 侧负责窗口、触摸与位置同步，网页侧负责大肥鱼自身的视觉和交互。

当前适配重点包括：

- Android WebView 本地资源加载
- ChatPage 全屏布局
- Android / JavaScript 坐标同步
- 拖动状态切换
- PopupWindow 尺寸切换
- 屏幕边界限制
- 设置页与 Web UI 面板之间的桥接
- RikkaHub 扩展页设置
- GitHub Actions Debug APK 构建

## 🚀 构建

项目使用 Android Studio / Gradle 构建，同时提供 GitHub Actions 自动构建 Debug APK。

# 🐟 大肥鱼移植战争实录：这条鱼到底挨过多少雷

> **警告：下面不是正式功能说明，而是一份灾难现场记录。**
>
> 本段故意放在 README 最后面。因为正常人看到项目 README 应该先知道“它是什么”，再知道“它曾经为什么差点游不起来”。

## 序章：事情本来没有这么复杂

最初的目标其实非常朴素：

**把 MeteorNOX 的大肥鱼塞进 RikkaHub，让它像原来一样工作。**

然后现实告诉我们：

> Web 页面自己跑是一回事，塞进 Android WebView、再套上 PopupWindow、再和 Compose 页面共存，是另一回事。

于是这条鱼正式进入了它漫长的受难史。

## 第一雷：鱼能显示，但“显示”不等于“能用”

最开始先解决的是最基本的集成：

`大肥鱼 Web UI → 本地资源 → Android WebView → RikkaHub ChatPage`

鱼终于出现了。

但这只是第一关。

网页原本默认自己拥有整个视口；放进 RikkaHub 后，它实际上住进了 Android 的 WebView，而 WebView 又被 PopupWindow 包起来。原本网页里理所当然的 `position: fixed`、viewport、鼠标/触摸坐标，突然都需要和 Android 的窗口坐标对账。

从这一刻开始，**坐标系就是本项目最大的反派之一。**

## 第二雷：一拖，瞬移到左上角

第一次真正接拖动时，出现了最经典的一幕：

> **手还没拖几下，大肥鱼直接瞬移到左上角。**

不是“拖得不够顺”，而是位置直接被重新解释。

根本原因是网页 root 的位置、WebView 本身的位置以及 PopupWindow 的位置并没有使用同一套坐标参考。

于是开始反复处理：

- `getBoundingClientRect()`
- WebView viewport 坐标
- Android PopupWindow 屏幕坐标
- root 的 left / top
- 窗口大小变化前后的坐标换算
- JavaScript → Android → JavaScript 的位置同步

## 第三雷：不是只能左上角，就是只能左上角附近

修完第一次瞬移以后，并没有结束。

新的表现变成：

> **鱼看起来可以动，但实际上只能在左上角一小块区域活动。**

手指明明已经拖得很远，网页里的坐标却被限制在原来的小区域里。

这时候才发现：把网页做成全屏、把 root 做成 fixed、再把 Android 窗口也跟着扩大，并不会自动让两套坐标系变成同一个世界。

## 第四雷：拖完以后，又跳回刚才的位置

继续修之后，又出现了一个非常具有欺骗性的 bug：

> **鱼明明被拖走了，松手之后却突然回到之前的位置。**

也就是说，视觉上的位置和 Android 侧保存的位置并没有在正确的时间完成同步。

于是不得不区分：

- 按下时的位置
- 真正开始拖动的位置
- 拖动过程中的 root rect
- PopupWindow 当前尺寸
- 松手时的位置
- 下一次窗口更新后的位置

拖动终于不再只是“监听 touchmove”这么简单。

## 第五雷：长按一下，鱼先抽搐一下

在解决瞬移后，又出现了一个更加诡异的问题：

> **长按大肥鱼准备拖动时，它会突然抽搐 / 跳一下。**

原因是“按下”本身就可能同时触发网页侧交互，而 Android 侧又在改变窗口交互状态。

于是加入了拖动阈值：

1. 先记录按下点。
2. 小范围移动只当作点击/长按准备。
3. 真正超过移动阈值后，才认定为拖动。
4. 到这一步才切换 Android 的交互窗口状态。

也就是说：

> **不动就别折腾窗口。**

## 第六雷：点击一下，也可能把鱼的位置改了

拖动问题修复过程中，还出现过一个很容易被忽略的副作用：

普通点击和拖动的状态切换混在一起，导致一次点击也可能触发重新定位。

这就是为什么后来要把：

`click ≠ drag`

明确区分开来。

大肥鱼不是每一次手指碰到它，都应该被 Android 重新摆放一次。

## 第七雷：设置页回来以后，鱼直接飞出屏幕

然后轮到设置页面。

进入设置之前鱼的位置正常。

设置页面回来以后：

> **鱼没了。**

更准确地说，是它可能已经被重新计算到了屏幕外。

PopupWindow 在设置期间发生了尺寸 / 布局变化，网页 root 保存的坐标再拿回来使用时，参考系已经变了。

于是加入了：

- 窗口尺寸变化后的重新定位
- 当前 root rect 记录
- 屏幕边界 clamp
- 返回聊天页面后的重新 pin

原则从此非常明确：

> **鱼可以游遍屏幕，但不许游出屏幕。**

## 第八雷：为了修坐标，PopupWindow 也被折腾了一遍

单纯改 JavaScript 已经解决不了问题。

Android 侧必须在“紧凑窗口”和“全屏交互窗口”之间切换。

于是又出现新的坑：

- PopupWindow 改尺寸的时机
- 改尺寸之后网页是否马上拿到了新 viewport
- Android 调 JavaScript 时网页到底处于哪个尺寸
- JS 发回的位置到底属于旧窗口还是新窗口

最后甚至加入了 UI 线程同步等待，让窗口切换完成后再继续通知网页重新固定 root。

一句话概括：

> **这已经不是养鱼了，这是在调教一个会自己换坐标系的窗口。**

## 第九雷：全屏 WebView 的副作用

曾经尝试过更激进的方案：让 WebView / 触摸代理尽可能覆盖整个聊天区域，然后统一处理事件。

结果又撞上新的问题：

- 无形的区域可能拦截触摸。
- 聊天页面本来应该响应的区域被大肥鱼层影响。
- 输入法 / 输入框交互受到影响。
- 页面响应出现卡顿。
- 启动和初始化变慢。

最终不能为了让一条鱼好拖，就把整个聊天页面赔进去。

所以后续方案转向**尽量小的窗口 + 必要时再切换交互状态**，而不是永久让一层透明的大东西盖在聊天页面上。

## 第十雷：无形框——看不见，但它就是能挡你

还有一种特别气人的问题：

> **屏幕上什么都没有，但手指就是点不到下面的东西。**

原因是透明 / 空白区域依然存在于触摸命中范围内。

这类问题肉眼看 UI 很难发现，因为你看到的是“空白”，系统看到的是“一个可以接收事件的 View / DOM 区域”。

于是需要同时控制：

- WebView 层级
- root 的实际尺寸
- modal mask 的范围
- pointer events
- 隐藏状态下的触摸拦截

这也是后来不断缩小实际交互区域的重要原因之一。

## 第十一雷：原版菜单和新需求打架

原版大肥鱼本身有自己的菜单。

但最终需求是：

> **大肥鱼本体不要再出现那个菜单，设置统一搬到 RikkaHub 的「扩展 → 大肥鱼」。**

问题是原版高级编辑器又藏在那个菜单后面。

于是不能简单粗暴地把整个功能删掉，只能做桥接：

`扩展页 → 请求对应面板 → 回到聊天页 → Web UI 打开原面板`

这才出现了现在的“设置页控制入口 + Web UI 保留编辑器”的结构。

## 第十二雷：设置页面有入口，但点了像没点

桥接做出来后，又发现：

> **扩展页的二级设置按钮能看到，但是点击以后什么都没发生。**

实际上请求已经被记录了，只是用户还停留在设置页，WebView 并没有马上重新加载并消费请求。

于是进一步修改为：

**点击高级编辑器 → 保存待打开动作 → 返回聊天页 → WebView 消费动作 → 打开对应面板。**

这才让“按钮真的有后续动作”。

## 第十三雷：设置内容一开始根本不够

最早的设置页并没有把需要控制的东西完整搬过来。

于是又补充了：

- 显示气泡
- 音效开关
- 音量
- 音效套装
- 用量模式
- 峰谷文案
- 每轮扣费提示
- 自动关闭
- 余额预警
- 今日预算
- 各类时间参数
- 滚动间隔
- 高级编辑器入口
- 恢复默认设置

设置页终于从“有个入口”变成了真正的设置页面。

## 第十四雷：什么东西都想做成 Slider

接着又发现一个 UI 设计上的雷：

某些参数虽然可以用 Slider，但金额和时间类参数用 0%～100% 的 Slider 就非常奇怪。

例如：

- 扣费提示关闭时间
- 余额预警阈值
- 今日预算
- 提醒显示时间
- 滚动间隔

最终这些改成了数字输入框，而百分比类设置才继续使用 Slider。

## 第十五雷：大小设置大战——最后被判处删除

移植过程中还折腾过“大肥鱼大小设置”。

它甚至一度出现在设置里，并且为了保存尺寸还增加了一套调试尺寸状态。

后来用户明确表示：

> **大小设置不要了。**

于是这套功能最终被整体撤掉，不再给用户一个看起来能调、实际上又容易和 WebView / PopupWindow 坐标产生连锁反应的入口。

这也是本项目少数真正意义上的“不是修好，而是删除”。

## 第十六雷：设置页 Kotlin 编译器开始报复

当 UI 终于看起来差不多时，轮到 Kotlin。

先后撞过各种设置页编译问题，包括 `PaddingValues + PaddingValues` 的 `Unresolved reference 'plus'` 等 Compose 类型 / Modifier 组合问题。

这种问题看截图基本看不出来，必须让 Gradle 真编译。

所以改成直接用合法的 `Modifier.padding(...)` 组合方式，而不是继续和类型系统硬刚。

## 第十七雷：一个括号，毁掉一整页

更离谱的一次是 `DaFeiYuSettingsPage.kt` 的花括号结构出了问题。

结果 Kotlin 编译器开始产生一串看起来互不相关的错误：

- `EditorButton` unresolved
- `private` 不能用于这里的局部声明
- 后面的 Composable 结构全部跟着报错

实际上根源只是前面的括号 / 作用域结构已经坏了。

这就是典型的：

> **第 154 行少一个 `}`，第 200 行开始全员陪葬。**

## 第十八雷：网页能编译，不代表 APK 能编译

还有一次非常经典：

大肥鱼 Web UI 的构建步骤成功了。

然后 Android Kotlin 编译失败。

也就是说：

> **“Web 构建成功”并不能证明“RikkaHub APK 能构建”。**

所以现在的验收标准必须是完整跑完：

`Web 构建 → Android 编译 → APK 打包 → Artifact 生成`

只完成其中一半，都不能算真正完成。

## 第十九雷：自动构建也加入战斗

为了让手机端开发方便，项目加入了 GitHub Actions 自动构建 Debug APK。

这样不用在手机上折腾完整 Android Studio 环境，只要代码推上 `master`，就可以让服务器负责：

- Gradle 构建
- Debug APK 打包
- 生成 arm64-v8a / x86_64 / universal 等产物
- 上传 Artifact

但这又产生了一个新的项目传统：

> **代码提交成功 ≠ 构建成功。**
>
> **构建开始 ≠ APK 已经出来。**
>
> **旧 Artifact ≠ 最新提交的 APK。**

所以以后只认实际构建结果，不认“应该已经好了”。

## 第二十雷：一次修复可能召唤出下一只雷

这次移植最明显的规律就是：

**修 A → 出 B → 修 B → 出 C → C 修完以后发现 A 的另一个分支还活着。**

例如：

`拖动` → `坐标` → `PopupWindow` → `viewport` → `返回设置` → `边界 clamp` → `菜单桥接` → `设置页` → `Kotlin 编译` → `Actions`。

所以这不是一条 bug list，而是一棵完整的 bug 家谱。

# 📜 最终开发守则

经过这一长串雷之后，这个项目留下了几条非常朴素的原则：

1. **能显示，不代表能用。**
2. **能拖，不代表坐标系正确。**
3. **点一下，不应该改变位置。**
4. **长按不应该先抽一下。**
5. **设置回来，鱼必须还在屏幕里。**
6. **透明区域也会挡触摸。**
7. **Web 构建成功，不等于 APK 构建成功。**
8. **提交成功，不等于 Actions 成功。**
9. **Actions 成功，不等于你手里的 APK 就是最新的。**
10. **没有实际验证，就不要说“完成”。**
